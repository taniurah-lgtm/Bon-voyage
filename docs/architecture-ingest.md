# 情報取り込みのアーキテクチャ

「403で読めない」「画像でしか出ていない」の2つを、どう構造で解くか。
結論だけ先に: **取得はCIで、解釈はセッションで。** 画像は**構造化＋人の承認**を必ず挟む。

---

## いま何が起きているか

| 症状 | 実体 | 例 |
|---|---|---|
| **403 で読めない** | このコンテナの外向き通信が許可リスト制。**技術的不具合ではなく設定** | `city.kodaira.tokyo.jp` / `asta.co.jp` / `mykoho.jp` / `docs.google.com` / 自サイト |
| **画像でしか出ていない** | そのページに文字が無い。ただし**同じサイトの別経路に文字がある場合が多い**(下記) | 月次スケジュールの一覧表、館内配布のチラシ |

**別々の問題。**混ぜて考えると解けない。

---

## 3層で分けて考える

```
[取得層] どこから取りに行くか
   1. このセッションから直取り  … 許可リスト次第。最も正確
   2. GitHub Actions から取得   … 外向き制限なし。既存の基盤がある
   3. 人がスクリーンショット     … 紙・画像しかない場合の最後の手段

[変換層] どうやって文字にするか
   A. HTML / JSON パース        … テキストがある場合
   B. PDF テキスト抽出          … pdftotext。テキスト層があれば最も確実
   C. 画像 → 視覚モデル          … 文字が無い場合。Gemini vision / チャットに貼る

[検証層] 台帳に入れる前に
   - 出典(URL または 紙面名)を必ず記録
   - 日付・締切・電話は人が承認する。視覚モデルの誤読が最も怖い
   - 前回スナップショットとの差分を取り「新着だけ」を出す
```

---

## 推奨: 「取得はCIで、解釈はセッションで」

**GitHub Actions が週次でソースを取得し、生スナップショットをリポジトリにコミットする。**
巡回セッションは git から読むだけなので、外向き通信が要らない。

```
.github/workflows/fetch-sources.yml  (週次 + 手動実行)
   └→ data/snapshots/YYYY-MM-DD/<source>.html / .pdf / .txt をコミット
        └→ 巡回セッションは snapshots を読んで台帳を起票
```

### プロキシと無関係に、これ自体が正しい設計である理由

1. **差分が取れる。** 「先週から増えたものだけ」が機械的に出る。
   いまは毎週ゼロから全部読み直していて、**新着の判定が人の記憶頼み**になっている。
2. **取りこぼしを検出できる。** 田無アスタは「毎回巡回」の設定なのに**毎月0件**だった。
   スナップショットがあれば「このソースは何週間も中身が取れていない」と分かる。
3. **再現性・監査可能性。** 何を見て起票したかが履歴に残る。日付を間違えたとき原因を追える。
4. **速い。** 巡回のたびに数十サイトを叩かなくてよい。

> ⚠️ 正直に言うと、これは 403 の回避にもなる。
> ただし**まず環境の許可リストを広げてもらうのが筋**(`docs/sources.md` 参照)。
> 直取りできれば要約ではなく原文が読め、精度が上がる。
> CI取得は「許可リストが広がっても、なお欲しい仕組み」として採るもので、
> 回避を目的に採るものではない。

## 画像をどう文字にするか(3ケースに分ける)

### ケース1: Webに PDF がある → **最優先で確認する価値あり**

**市報こだいらは、各号の目次ページから PDF がリンクされている。**
さらに「マイ広報紙」(`mykoho.jp`)に**テキストで転載**されている。

→ **PDFにテキスト層があれば `pdftotext` だけで済み、スクリーンショットは不要になる。**
　 許可リストが開いたら真っ先に確認する。ここが通れば月2回の手作業が消える。

```bash
curl -sL "<市報のPDF URL>" -o shihou.pdf && pdftotext -layout shihou.pdf -
```

### ケース2: 一覧は画像だが、別経路に文字がある ← **まずこれを疑う**

**❌ 2026-08 の失敗**: 田無アスタの月次スケジュールが画像だったので、
「このサイトはWebに文字が無い」と結論し、スクリーンショット運用を設計に組み込んだ。
**誤りだった。** `asta.co.jp/event/` に**イベント名・日時・場所が本文テキストで載っていた**。
一覧表しか見ずに、サイト内の別経路を確認しなかったのが原因。

**教訓 —「読めない」と判断する前に、必ず次を全部見る**:

1. **個別ページ**(`/event/`・イベント詳細)… 一覧が画像でも、詳細はHTMLのことが多い
2. **PDF**(`pdftotext -layout`。`poppler-data` を入れる)
3. **別の一覧**(お知らせ・新着・アーカイブ)
4. **それでも無ければ**、はじめて画像として読む

**画像でしか取れない項目もある。** アスタの場合、参加費・定員はチラシPDF(画像)側にしかなかった。
→ **本文テキストで骨格を取り、画像で細部を補う**のが正しい形。

### ケース3: 紙しかない

**❌ 訂正**: 以前ここに「スクリーンショットをチャットに貼るのが最も精度が高い」と書いていたが、
**測定して否定された**。

| 経路 | 実測の誤り |
|---|---|
| **画像をClaudeが読む** | 市報 **11件中4件(36%)**。アスタも参加費の欠落・時刻ずれ・イベント性質の取り違え |
| PDFテキスト抽出 | 誤りゼロ(ただし縦組みは `-bbox` で座標から組み直す必要あり) |

**画像を読むのは最後の手段。** そして読んだものは `確度: 未検証` を付け、裏が取れるまで配信に載せない。

## 検証層(ここを省くと事故る)

視覚モデルもGeminiも**誤読する**。特に日付・締切・電話番号。

- 台帳の各項目に **`確度:`** を必ず書く(`公式確認済み` / `市報掲載` / `要確認`)
- **申込締切があるものは人が二重確認する。** 締切を1日間違えると読者に実害が出る
- **住所・電話は、出典を示せないものを入れない**
  (2026-08、Geminiにアポリストを作らせたら全件「要確認」で、施設の所在まで取り違えた)

> 現状の弱点: 市報から起票した E44〜E54 は、**紙面を読んだのが私だけ**で人の確認を経ていない。
> 締切のある E46/E48/E50 は、配信前にオーナーが紙面と突き合わせること。

## 実装の順番(費用対効果順)

| # | やること | 効果 | 工数 |
|---|---|---|---|
| 1 | **環境の許可リストを広げてもらう** | 大(全部の精度が上がる) | ゼロ(設定) |
| 2 | **市報PDFのテキスト層を確認** | 大(月2回の手作業が消えるかも) | 小 |
| 3 | `fetch-sources.yml` でスナップショット＋差分 | 大(新着判定が機械化) | 中 |
| 4 | アスタ画像 → Gemini vision → JSON → 承認 | 中 | 中 |
| 5 | 紙のスクショ運用 | — | 現状維持でよい |

**1と2が終わるまで、3以降は着手しない。**1で解決するかもしれないものに、先に仕組みを被せない。
