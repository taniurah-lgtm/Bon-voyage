# 配信事故の記録と、二重化した監視の設計

**「配信できたか」を人間が思い出す運用は、6回連続で失敗した。**このファイルはその記録と、対策の設計。

---

## 事故の一覧（2026年）

| 日 | 壊れ方 | LINE配信 | リポジトリ記録 | 発見 |
|---|---|---|---|---|
| 07-22 | push失敗 | ✅ 届いた | ❌ 残らず | 後日 |
| 07-29 | push失敗 | ✅ 届いた | ❌ 残らず | 後日 |
| 08-05 | push失敗 | ✅ 届いた（46通） | ❌ 残らず | **8/19まで気づかず** |
| 08-12 | push失敗 | ✅ 届いた（46通） | ❌ 残らず | **8/19まで気づかず** |
| 08-26 | 承認待ちで停止 | ❌ 未配信 | ❌ | オーナーが当日発見 |
| **09-02** | **78秒で自己終了** | ❌ 未配信 | ❌ | **10時間34分後** |

**型が2つある。混同すると原因を取り違える。**

- **型A（07-22〜08-12）**: LINEには届いたが push が落ちて記録が消えた。
  原因は非fast-forward（毎朝07:00のSNS草案ワークフローが同じブランチに先にコミットする）。
  → `scripts/publish_report.sh` に `pull --rebase` 込みの push を閉じ込め、**pushが通ったときだけLINEを送る**順序にして解決。
- **型B（08-26・09-02）**: そもそも巡回セッションが仕事をしなかった。**LINEには何も届いていない。**

## 2026-09-02 の解剖

ルーティンの実行ログで確定した事実:

| 項目 | 記録 |
|---|---|
| 発火 | **した**（09:08 JST）。「発火しなかった」は誤診 |
| 記録上の結果 | `ROUTINE_RUN_STATUS_SUCCEEDED` |
| 実行時間 | **00:08:43Z → 00:10:00Z ＝ 78秒** |
| 成果物 | コミット0・LINE配信0（`totalUsage` は当時0） |
| 実行モデル | **claude-sonnet-5**（ルーティンに model 未設定だったため） |
| 出力 | 4,770トークン ＝ **長い文章を書いて止まった** |

**78秒が全て。**巡回は本来10〜30分かかる。1分で終わった時点で中身は何もしていない。

### 原因（確度順）

1. **プロンプトが「止まれ」と教えていた。**当時の文面には停止指示が4か所あり、
   とどめが「※2026年9月は水曜が5回あり…**月内のどこかで必ず止まる**」。
   **9/2は9月最初の水曜。**冒頭でこれを読めば「今月は止まって報告する月だ」と読める。
   **事故防止のつもりで書いた行が、事故を起こした。**
2. **モデルが固定されていなかった。**`model: ""` のため Sonnet 5 で実行。
   この手順書は Opus のセッションで書いて調整したもの。4,000字・6段階・条件分岐だらけの指示で、
   しかも「迷ったら止まれ」と繰り返し書いてある。いちばん安全に見える分岐が「報告して終わる」だった。
3. **「成功」の定義が間違っていた。**`SUCCEEDED` は「セッションが落ちなかった」の意味で、
   配信の成否とは無関係。完了通知(push)も、何もしなかった完了で鳴る。

> 🔑 **いちばんの教訓: 死んだセッションは、自分が死んだことを報告できない。**
> 巡回セッション自身に生存確認をさせる設計に、そもそも無理があった。

---

## 対策（2026-09-04 実装）

### 1. 巡回ルーティンの是正

- **モデルを `claude-opus-5` に固定**
- **「今月は必ず止まる」の予告を削除。**失敗を先に宣言しない。無料枠は事実だけ書く
- 事故の歴史を冒頭から撤去（この `docs/delivery-incidents.md` に移した）
- **完了条件を明文化**:
  > **(A) 配信まで成功した / (B) エラー原文とレポート全文を出した — どちらかに到達するまで終わらない**
- **「数分で終わった巡回は失敗である」と明記**し、78秒の前例を根拠として書く
- **原稿を調査より先に作る**（手順2）。ファイルが先に存在すれば、あとから手で復旧できる

### 2. 見張りルーティンを別に立てた（水 11:30 JST / cron `30 2 * * 3` UTC）

**別のセッションが、外から数字を見る。**

- `reports/free/<今日>.md` の有無 と `totalUsage` を突き合わせる
- 正常 → **何もしない。**1行だけ報告して終了（コミットもpushもしない）
- 異常 → **報告して終わらず、その場で巡回をやり直して配信する**
- すでに `totalUsage` が増えていたら型Aなので、**LINEは送らずコミットとpushだけ**（二重配信の防止）
- 通知は push ＋ **メール**（巡回本体は push のみ。見張りは確実に届かせる）

**発見までの時間: 10時間34分 → 2時間半。**

## 判定に使う数字（これ以外を信じない）

```bash
# 実配信のリアルタイムな証拠はこれだけ
curl -sS -H "Authorization: Bearer $LINE_CHANNEL_ACCESS_TOKEN" \
  "https://api.line.me/v2/bot/message/quota/consumption"     # → {"totalUsage":47}

# 到達人数（ブロック除く）
curl -sS -H "Authorization: Bearer $LINE_CHANNEL_ACCESS_TOKEN" \
  "https://api.line.me/v2/bot/insight/followers?date=YYYYMMDD"
```

- ⚠️ **当日分の `insight/message/delivery` は `unready` を返す。**当日の判定には使えない
- ⚠️ **リポジトリのファイルは「記録」であって「配信」ではない。**両方を見ないと状態が分からない
- ⚠️ **ルーティンの `SUCCEEDED` は配信の証拠ではない**
