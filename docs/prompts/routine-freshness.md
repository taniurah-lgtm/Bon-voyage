## なぜこの仕事があるか

**台帳には、観光協会のカレンダーから拾った「1行だけ」の回が溜まる。**
そのまま号に出す直前まで放置され、直前に調べると中身が化けることが続いた。

- **E116 新小平マーケット** … 1行だけだった → 調べたら**子ども駅長の制服体験**があった
- **E117 親子うどん打ち体験会** … 1行だけだった → **申込開始が2日後・先着**だった
- **E134 小平市民まつり** … 市の常設ページは前年のまま。**市報にだけ今年の日付**があった

🔴 **公式は「あとから」更新される。こちらが見に行かないと気づけない。**
**号を作る日に慌てて調べるのではなく、毎朝すこしずつ潰しておく。**

## 手順3 台帳を直す

- **取れたものだけ**を書き足す。**取れなかったものの「(要確認)」は外さない**
- 🔴 **推測で埋めない。**「たぶん無料」は書かない（`CLAUDE.md`「『無料』と書く前に、費用を必ず確認する」）
- 🔴 **読者に見せる行には、結果だけを書く。**理由・迷い・日付つきのメモは
  **`- 内部メモ: 〜` の行**に置く。
  （2026-09-21、料金欄に「『無料』と断定しない」が出たまま公開されていた）
- **確度の行に、確認した日を必ず残す**。例: `- 確度: **公式確認済み（2026-09-22）**`
  **これが無いと、翌日また同じ回が出てくる**
- **年齢の目安（👶🧒🎒 を ◎○△✕）が無ければ、内容から付ける**。
  対象学年が決まっているものは、その外を ✕ にする

## 手順4 作り直して、確かめて、push

```bash
node scripts/build-events-json.mjs && node scripts/build-calendar.mjs
```

🔴 **ビルドの最後に出る検査を必ず読む。**
`🔴 内部の判断が公開データに ◯件 出ています` が出たら、**その回の台帳を直してから push する。**

```bash
git add -A
git commit -m "裏取り: <ID> ほか<n>件（<日付>）"
git pull --rebase origin claude/family-event-planning-rfwmo8
git push -u origin claude/family-event-planning-rfwmo8
```

- **変わっていなければ commit しない。**空のコミットを作らない
- push が失敗したら 2s → 4s → 8s → 16s で最大4回やり直す

## 🔴 確認日は「確度」の行に YYYY-MM-DD で書く（2026-09-22 追加）

**`stale-check` は `- 確度:` の行から `20\d\d-\d\d-\d\d` を探している。**
**この形で日付が無いと、翌日もまた同じ回が出てくる。**

```
⭕️ - 確度: **公式確認済み（2026-09-22）**
❌ - 確度: **公式確認済み**              ← 日付が無い。明日また出てくる
❌ - 確度: **主催者に確認済み**           ← 同上
```

**取れなかった項目があっても、確認した日は書く。**
「見に行ったが、公式に記載が無かった」も確認のうち。

## 🔴 「この通信の宛先に合わない」ものは、候補のまま置かない

**候補のまま置くと、毎朝この仕事に出てきて、毎朝同じ判断をやり直すことになる。**
